# Алертинг у Grafana

Стан на 2026-09-03. Алерти лишаються в Grafana, а не в боті — рішення
зафіксоване в `.claude/tasks/README.md`.

Правила живуть у папці `Deye Alerts`, група `Battery Monitoring`, інтервал
оцінювання 1 хв, contact point `Telegram Deye Battery` (тип telegram, шле в
той самий чат, що й бот). Реальні UID — у `.claude/infra.local.md`.

## Пастка, через яку алерти мовчали

**Grafana шле повідомлення в Telegram з `parse_mode: HTML`. Будь-який символ
`<` у назві правила чи в анотаціях ламає доставку цілком.**

Telegram відповідає:

```
400 Bad Request: can't parse entities: Unsupported start tag "" at byte offset 688
```

Повідомлення не доходить. У Telegram — тиша. У UI Grafana правило показує
нормальний стан «firing», ніби все спрацювало. Помилку видно лише тут:

```
GET /api/alertmanager/grafana/config/api/v1/receivers
→ integrations[0].lastNotifyAttemptError
```

Правило називалось **`🔋 Deye Battery SOC < 20%`**. Назва потрапляє в тіло
повідомлення як `alertname`, тож **це правило не могло доставити жодного
сповіщення від моменту створення**. Якби заряд справді впав нижче 20%,
повідомлення так само впало б з 400.

Перейменовано на `🔋 Заряд батареї нижче 20%`. Правило перевірене живою
доставкою.

**Правило на майбутнє: у назвах і анотаціях алертів не вживати `<` і `>`.**
Писати «нижче 20%», а не «SOC < 20%». Це стосується будь-якого тексту, що
йде в Telegram — включно з описами, які здаються суто внутрішніми.

Системна альтернатива — виставити в contact point `parse_mode: None`, тоді
Telegram не намагатиметься парсити розмітку взагалі. Наразі не робили: щоб
змінити налаштування, треба переслати й `bottoken`, а він віддається
редагованим (`[REDACTED]`), тож є ризик затерти токен. Через UI це безпечно —
варто зробити, якщо алертів побільшає.

## Тексти повідомлень

Типовий шаблон Grafana шле в Telegram службовий дамп: `Value: [no value]`,
список labels з `datasource_uid` і `ref_id`, обидві анотації з іменами полів,
плюс два довгі URL. Для людини, яка просто відповідає за будинок, це нечитабельно.

Тому вбудований шаблон **перевизначено**. Notification template `deye-telegram`
оголошує `default.message` — Grafana бере визначення користувача замість свого,
і **contact point чіпати не треба** (а це важливо: `bottoken` віддається через
API як `[REDACTED]`, тож PUT на contact point ризикує затерти токен).

```
{{ define "default.message" }}
{{- range .Alerts.Firing }}
{{ .Annotations.summary }}

{{ .Annotations.description }}
{{- end }}
{{- range .Alerts.Resolved }}
✅ Все гаразд — {{ .Annotations.resolved }}
{{- end }}
{{ end }}
```

Звідси випливає контракт для анотацій кожного правила:

| Анотація | Роль | Стиль |
|---|---|---|
| `summary` | перший рядок, суть | коротко, з емодзі |
| `description` | що це означає й що робити | 2–3 речення звичайною мовою |
| `resolved` | хвіст рядка відбою | у називному, з малої літери |

Було й стало:

```
**Firing**                                📡 Немає даних з інвертора
Value: [no value]
Labels:                                   Показники не надходять уже понад
 - alertname = 📡 Дані з інвертора…       45 хвилин. Зараз невідомо, який
 - datasource_uid = <GRAFANA_DS_UID>        заряд батареї — і якщо він впаде,
 - grafana_folder = Deye Alerts           попередження не прийде.
 - ref_id = A
Annotations:                              Потрібно перевірити моніторинг.
 - description = …
 - grafana_state_reason = NoData
 - summary = …
Source: https://…
Silence: https://…
```

Відбій — один рядок: `✅ Все гаразд — дані з інвертора знову надходять`.

Технічні подробиці (які саме команди дивитись) навмисно **прибрані з
повідомлень** — вони тут, у цьому файлі. Сповіщення має відповідати на
«що сталось і чи це страшно», а не на «як полагодити».

## Хибні спрацювання через закоротке вікно (виправлено 4 вер 2026)

Уночі прийшло «🔋 Заряд батареї нижче 20% — батарея майже розряджена», хоча
SOC весь час був 98%. Історія станів правила показала справжню причину:

```
2026-09-04 00:05:40   Normal → Pending (Nodata)
2026-09-04 00:08:40   Pending (Nodata) → Nodata → Normal (Missingseries)
2026-09-03 20:40:40   Normal → Pending (Nodata)      ← те саме двома годинами раніше
```

Запит правила брав **`range(start: -10m)`**, а колектор пише раз на **10–15
хвилин** — реальний каданс хмари Deye. Тобто вікно регулярно виявлялось
порожнім при цілком живих даних, правило йшло в `NoData`, а `noDataState:
NoData` перетворював це на сповіщення.

Гірше за сам факт: шаблон не відрізняв NoData від справжнього спрацювання, тож
людина бачила «батарея майже розряджена» замість «дані не надійшли». Це рівно
той тип хибної тривоги, після якого алерти починають ігнорувати.

**Що змінено:**

1. Вікно правила SOC: `-10m` → **`-45m`**. `last()` усе одно бере найсвіжішу
   точку, тож ширше вікно нічого не спотворює — воно лише перестає бути
   порожнім між двома записами.
2. `noDataState` правила SOC: `NoData` → **`OK`**. Реальну відсутність даних
   ловить окреме правило «Дані з інвертора не надходять» з тим самим вікном
   45 хв. Дублювати це в правилі про заряд означало слати друге сповіщення,
   ще й з текстом про розряджену батарею.
3. Шаблон навчено розрізняти: якщо `grafana_state_reason` = `NoData`,
   повідомлення каже «немає даних для перевірки», а не текст правила.
   Це страхувка на майбутні правила.

**Правило на майбутнє: вікно запиту в алерті мусить бути помітно ширшим за
каданс надходження даних.** Для цього проєкту каданс — 10–15 хв, тож нижча
межа це ~30 хв, а обрано 45.

> Перевимір 7 вер 2026 (`deye-cloud-api.md`) показав каданс ~5 хв, а не
> 10–15. Вікна 45 хв від цього стають лише консервативнішими — міняти їх
> не треба. А от **затримка виявлення лишалась розрахованою на старе
> число**: правило 4 обіцяло в тексті «сповіщення могло затриматись на
> 10–15 хвилин», хоча реально це ~5. Виправлено 9 вер 2026 на «5-10
> хвилин» — разом зі скороченням `COLLECT_INTERVAL` до 90 с. Текст живе в
> анотації правила в Grafana, не в репозиторії: правиться тільки там, і
> зміна створює нову версію правила (тепер 4-ту).

## Правило 1 — заряд нижче 20%

Запит бере останній `soc` у вікні **45 хв**, поріг «нижче 20», `for: 1m`,
`noDataState: OK` (див. розділ вище — чому саме так).

- summary: `🔋 Заряд батареї нижче 20%`
- description: `Батарея майже розряджена. Якщо зникне світло, резерву вистачить ненадовго.`
- resolved: `заряд батареї піднявся вище 20%`

## Правило 2 — дані не надходять (нове)

Відповідає на питання «а чи взагалі працює моніторинг». Без нього зупинка
збору виглядає як тиша, тобто як «все добре» — рівно те, що сталося
10 лип 2026 і чого ніхто не помітив до вересня.

```flux
from(bucket: "monitoring")
  |> range(start: -45m)
  |> filter(fn: (r) => r._measurement == "battery" and r._field == "soc")
  |> group()
  |> count()
```

| Параметр | Значення |
|---|---|
| Назва | `📡 Дані з інвертора не надходять` |
| Умова | `count() < 1` (reduce `last` → threshold) |
| `for` | 5 хв |
| `noDataState` | **`Alerting`** |
| `execErrState` | `Alerting` |

- summary: `📡 Немає даних з інвертора`
- description: `Показники не надходять уже понад 45 хвилин. Зараз невідомо, який заряд батареї — і якщо він впаде, попередження не прийде.` + `Потрібно перевірити моніторинг.`
- resolved: `дані з інвертора знову надходять`

Механіка: якщо точок немає, Flux повертає **порожньо** — не нуль. Порогова
умова при цьому не обчислюється взагалі, спрацьовує гілка NoData. Саме тому
`noDataState` мусить бути `Alerting`, а не типовий `NoData`: тоді приходить
звичайний алерт з нашим текстом, а не службовий `DatasourceNoData`.

Вікно 45 хв обране за виміряним кадансом хмари Deye (10–15 хв між
`collectionTime`). Порожнє вікно на 45 хв — це вже втричі більше за
найдовший спостережений розрив, тож хибних спрацювань бути не має.
Разом з `for: 5m` збій виявляється приблизно за 50 хвилин.

## Як тестувати алерт, не чекаючи справжнього збою

Тимчасово звузити вікно до `-1m`: точки надходять раз на ~5 хв, тож
вікно буде порожнім і правило піде тим самим шляхом NoData → Alerting.
Після перевірки повернути `-45m`.

Два нюанси, на які натрапили:

1. **Grafana не оновлює анотації вже запущеного інстансу.** Якщо правило
   горить і виправити текст анотації, у Telegram і далі піде старий текст.
   Треба спершу дати правилу перейти в Normal, і лише тоді запалювати знову.
2. Alertmanager групує за `[grafana_folder, alertname]`, `group_interval`
   типово 5 хв — між повторними надсиланнями буває помітна пауза.

## Правило 3 — обʼєкт замовк (додано 4 вер 2026)

Правило 2 ловить «немає взагалі нічого». Коли обʼєктів більше одного, цього
замало: якщо замовкне один із трьох, точки решти двох тримають лічильник
непорожнім, і правило мовчить.

Розвʼязання — рахувати не наявність, а **вік** останньої точки, окремо на
кожен інвертор:

```flux
from(bucket: "monitoring")
  |> range(start: -6h)
  |> filter(fn: (r) => r._measurement == "battery" and r._field == "soc")
  |> group(columns: ["inverter"])
  |> last()
  |> map(fn: (r) => ({ r with _value: (float(v: uint(v: now())) - float(v: uint(v: r._time))) / 1000000000.0 }))
  |> keep(columns: ["_time", "_value", "inverter"])
```

| Параметр | Значення |
|---|---|
| Умова | вік останньої точки `> 2700` с (45 хв) |
| `for` | 5 хв |
| `noDataState` | `OK` — повну тишу ловить правило 2, тут це був би дубль |

`group(columns: ["inverter"])` дає **окремий інстанс алерту на кожен обʼєкт**,
тож повідомлення каже, хто саме замовк — через `{{ $labels.inverter }}`.

Межа підходу, про яку варто знати: обʼєкт, що мовчить понад **6 годин**,
випадає з вікна запиту й зникає з результату — на відсутню серію алерт не
побудуєш. Саме цей випадок і покриває правило 2.

## Правило 4 — немає живлення від мережі (додано 4 вер 2026)

Найкорисніше сповіщення з чотирьох: воно каже, що резерв **почав** витрачатися,
тоді як «заряд нижче 20%» попереджає вже наприкінці. Для ліфта в житловому
будинку різниця між цими двома моментами — це години.

Дані для нього збирає колектор в окремий вимір `grid`:

```
measurement: grid
tags:   inverter=<SN>
fields: voltage (float, максимум трьох фаз)
        frequency (float)
        power (float)
```

```flux
from(bucket: "monitoring")
  |> range(start: -45m)
  |> filter(fn: (r) => r._measurement == "grid" and r._field == "voltage")
  |> group(columns: ["inverter"])
  |> last()
```

| Параметр | Значення |
|---|---|
| Умова | напруга `< 50` В |
| `for` | `0s` |
| `noDataState` | `OK` — відсутність даних ловлять правила 2 і 3 |

**Чому максимум трьох фаз.** Втрата однієї фази — це не блекаут: інвертор досі
має мережу. Нулем максимум стає лише тоді, коли зникли всі три.

**Чому поріг 50 В.** Значно нижче за будь-яку реальну мережу навіть у глибокій
просадці й значно вище за шум давача. Проміжних значень тут не буває: або
~230 В, або нуль.

**Чому `for: 0s`, а не вікно з `max()`.** Варіант «усі точки за 25 хвилин нижче
порогу» захистив би від одиничного викиду, але додав би до затримки ще довжину
вікна. Реальна нижня межа тут і так — **каданс вивантаження в хмару, ~5
хвилин**, і подвоювати її заради захисту від малоймовірного викиду не варте
того: подія, заради якої все робиться, триває годинами. Ціна рішення: одне
хибне нульове показання дасть хибну тривогу, яка сама згасне за 15 хвилин.

**Затримку названо в самому повідомленні** — «сповіщення могло затриматись на
5-10 хвилин» (до 9 вер 2026 — «10–15»). Людина, яка сидить у темряві вже
десять хвилин, інакше вирішить, що система не працює. Число має лишатись
чесним: воно перевіряється кадансом хмари, а не нашим бажанням.

## Правило 5 — інвертор відʼєднався від мережі (додано 9 вер 2026)

Правило 4 ловить блекаут по напрузі. Виявилось, що цього замало.

**Як знайшли.** Застосунок Deye прислав «відключення електромережі»
29 сер 2026 о 14:27, а в телеметрії того дня напруга не падала жодного разу
(мінімум за добу — 229.5 В). Пошук по `device/history` дав відповідь:

```
час             GridP  GridI  GridV   BattP  UPSload
08-29 14:22:06    187   0.80    233      52      187
08-29 14:27:13      0   0.00    233     286      241   ← сповіщення
08-29 14:32:20    718   1.18    233    -396      224
```

Струм мережі рівно нуль, напруга нормальна, а батарея підхопила рівно
навантаження — 286 Вт проти 241 Вт споживання. Баланс сходиться, тож це не
артефакт вимірювання: будинок цю хвилину жив від батареї.

**База за 15 діб** (26 сер — 9 вер, 4251 кадр): таких подій дві — 29 сер
14:27 і 30 сер 04:00. Розділення чисте: у подіях струм 0.00 A, а найближчий
кандидат серед решти — 0.64 A. По потужності запас вужчий (0 проти 8 Вт),
тому поріг стоїть саме на струмі.

| Параметр | Значення |
|---|---|
| Умова | `grid.current` нижче 0.1 A **і** `grid.voltage` не нижче 50 В |
| `for` | `0s` |
| `noDataState` | `OK` — тишу ловлять правила 2 і 3 |
| `execErrState` | `OK` — помилка виразу не має будити людину вночі |

Запит — два незалежні: A (струм) і C (напруга), кожен `group(columns:
["inverter"])` + `last()`, далі `reduce(last)` і math-вираз
`($B < 0.1) && ($D >= 50)`. Саме два запити, а не один із `pivot`: якби
колонки не було (пристрій не віддає струм, або його ще немає в бакеті),
`pivot` дав би помилку «record is missing label», а math просто не поверне
інстанс.

**Чому `for: 0s`.** Обидві відомі події тривали **менше одного кадру** — по
одній точці кожна. Будь-яке вікно очікування пропустило б їх повністю.
Зворотний бік: одне хибне нульове показання дасть хибну тривогу. Прийнято
свідомо, як і в правилі 4.

**Межа підходу.** На цій станції немає PV, тому струм ніколи не проходить
через нуль природно. Там, де сонце є, баланс імпорт/експорт даватиме нулі
регулярно, і поріг стане джерелом хибних тривог — для таких обʼєктів
знадобиться підтвердження розрядом батареї.

**Перевірено без сповіщень:** прогоном пайплайна через `/api/ds/query` з
підміненим порогом. При 5 A замість 0.1 загорілись рівно ті два обʼєкти, у
яких струм менший за 5 A, а третій (7.55 A) лишився спокійним. Підміна
умови на «напруга не нижче 400 В» гасить усі три — тобто під час блекауту
правило справді мовчить.

## Мультиінверторність (задача 12, 4 вер 2026)

Правило 1 теж переведено на `group(columns: ["inverter"])`. Без цього два
обʼєкти дали б або помилку «input data must be a wide series», або схлопування
в одне значення — і повідомлення не сказало б, у кого саме сів акумулятор.

У `summary` і `resolved` додано `{{ $labels.inverter }}`. Grafana підставляє
значення перед відправкою, тож і telegram-канал адміна, і бот отримують уже
готовий текст.
