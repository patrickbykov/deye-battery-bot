# Алертинг у Grafana

Стан на 2026-09-03. Алерти лишаються в Grafana, а не в боті — рішення
зафіксоване в `.claude/tasks/README.md`.

Правила живуть у папці `Deye Alerts`, група `Battery Monitoring`, інтервал
оцінювання 1 хв, contact point `Telegram Deye Battery` (тип telegram, шле в
той самий чат, що й бот). Реальні UID — у `.claude/infra.local.md`.

## Пастка, через яку алерти мовчали

**Grafana шле повідомлення в Telegram з `parse_mode: HTML`. Будь-який символ
`<` у назві правила чи в анотаціях ламає доставку цілком.**

Telegram відповідає:

```
400 Bad Request: can't parse entities: Unsupported start tag "" at byte offset 688
```

Повідомлення не доходить. У Telegram — тиша. У UI Grafana правило показує
нормальний стан «firing», ніби все спрацювало. Помилку видно лише тут:

```
GET /api/alertmanager/grafana/config/api/v1/receivers
→ integrations[0].lastNotifyAttemptError
```

Правило називалось **`🔋 Deye Battery SOC < 20%`**. Назва потрапляє в тіло
повідомлення як `alertname`, тож **це правило не могло доставити жодного
сповіщення від моменту створення**. Якби заряд справді впав нижче 20%,
повідомлення так само впало б з 400.

Перейменовано на `🔋 Заряд батареї нижче 20%`. Правило перевірене живою
доставкою.

**Правило на майбутнє: у назвах і анотаціях алертів не вживати `<` і `>`.**
Писати «нижче 20%», а не «SOC < 20%». Це стосується будь-якого тексту, що
йде в Telegram — включно з описами, які здаються суто внутрішніми.

Системна альтернатива — виставити в contact point `parse_mode: None`, тоді
Telegram не намагатиметься парсити розмітку взагалі. Наразі не робили: щоб
змінити налаштування, треба переслати й `bottoken`, а він віддається
редагованим (`[REDACTED]`), тож є ризик затерти токен. Через UI це безпечно —
варто зробити, якщо алертів побільшає.

## Тексти повідомлень

Типовий шаблон Grafana шле в Telegram службовий дамп: `Value: [no value]`,
список labels з `datasource_uid` і `ref_id`, обидві анотації з іменами полів,
плюс два довгі URL. Для людини, яка просто відповідає за будинок, це нечитабельно.

Тому вбудований шаблон **перевизначено**. Notification template `deye-telegram`
оголошує `default.message` — Grafana бере визначення користувача замість свого,
і **contact point чіпати не треба** (а це важливо: `bottoken` віддається через
API як `[REDACTED]`, тож PUT на contact point ризикує затерти токен).

```
{{ define "default.message" }}
{{- range .Alerts.Firing }}
{{ .Annotations.summary }}

{{ .Annotations.description }}
{{- end }}
{{- range .Alerts.Resolved }}
✅ Все гаразд — {{ .Annotations.resolved }}
{{- end }}
{{ end }}
```

Звідси випливає контракт для анотацій кожного правила:

| Анотація | Роль | Стиль |
|---|---|---|
| `summary` | перший рядок, суть | коротко, з емодзі |
| `description` | що це означає й що робити | 2–3 речення звичайною мовою |
| `resolved` | хвіст рядка відбою | у називному, з малої літери |

Було й стало:

```
**Firing**                                📡 Немає даних з інвертора
Value: [no value]
Labels:                                   Показники не надходять уже понад
 - alertname = 📡 Дані з інвертора…       45 хвилин. Зараз невідомо, який
 - datasource_uid = aff44z3iv9fy8d        заряд батареї — і якщо він впаде,
 - grafana_folder = Deye Alerts           попередження не прийде.
 - ref_id = A
Annotations:                              Потрібно перевірити моніторинг.
 - description = …
 - grafana_state_reason = NoData
 - summary = …
Source: https://…
Silence: https://…
```

Відбій — один рядок: `✅ Все гаразд — дані з інвертора знову надходять`.

Технічні подробиці (які саме команди дивитись) навмисно **прибрані з
повідомлень** — вони тут, у цьому файлі. Сповіщення має відповідати на
«що сталось і чи це страшно», а не на «як полагодити».

## Правило 1 — заряд нижче 20%

Те, що було, з виправленою назвою й текстами. Запит бере останній `soc`,
поріг «нижче 20», `for: 1m`, `noDataState: NoData`.

- summary: `🔋 Заряд батареї нижче 20%`
- description: `Батарея майже розряджена. Якщо зникне світло, резерву вистачить ненадовго.`
- resolved: `заряд батареї піднявся вище 20%`

## Правило 2 — дані не надходять (нове)

Відповідає на питання «а чи взагалі працює моніторинг». Без нього зупинка
збору виглядає як тиша, тобто як «все добре» — рівно те, що сталося
10 лип 2026 і чого ніхто не помітив до вересня.

```flux
from(bucket: "monitoring")
  |> range(start: -45m)
  |> filter(fn: (r) => r._measurement == "battery" and r._field == "soc")
  |> group()
  |> count()
```

| Параметр | Значення |
|---|---|
| Назва | `📡 Дані з інвертора не надходять` |
| Умова | `count() < 1` (reduce `last` → threshold) |
| `for` | 5 хв |
| `noDataState` | **`Alerting`** |
| `execErrState` | `Alerting` |

- summary: `📡 Немає даних з інвертора`
- description: `Показники не надходять уже понад 45 хвилин. Зараз невідомо, який заряд батареї — і якщо він впаде, попередження не прийде.` + `Потрібно перевірити моніторинг.`
- resolved: `дані з інвертора знову надходять`

Механіка: якщо точок немає, Flux повертає **порожньо** — не нуль. Порогова
умова при цьому не обчислюється взагалі, спрацьовує гілка NoData. Саме тому
`noDataState` мусить бути `Alerting`, а не типовий `NoData`: тоді приходить
звичайний алерт з нашим текстом, а не службовий `DatasourceNoData`.

Вікно 45 хв обране за виміряним кадансом хмари Deye (10–15 хв між
`collectionTime`). Порожнє вікно на 45 хв — це вже втричі більше за
найдовший спостережений розрив, тож хибних спрацювань бути не має.
Разом з `for: 5m` збій виявляється приблизно за 50 хвилин.

## Як тестувати алерт, не чекаючи справжнього збою

Тимчасово звузити вікно до `-1m`: точки надходять раз на 10–15 хв, тож
вікно буде порожнім і правило піде тим самим шляхом NoData → Alerting.
Після перевірки повернути `-45m`.

Два нюанси, на які натрапили:

1. **Grafana не оновлює анотації вже запущеного інстансу.** Якщо правило
   горить і виправити текст анотації, у Telegram і далі піде старий текст.
   Треба спершу дати правилу перейти в Normal, і лише тоді запалювати знову.
2. Alertmanager групує за `[grafana_folder, alertname]`, `group_interval`
   типово 5 хв — між повторними надсиланнями буває помітна пауза.

## Що ще не зроблено

**Простій по кожному інвертору окремо.** Поточне правило ловить лише
ситуацію «немає взагалі нічого». Якщо інверторів стане два і замовкне один,
його серія просто зникне з результату, а не стане нулем — а на відсутню
серію алерт не побудуєш. Потрібен інший підхід: або окреме правило на
кожен SN, або порівняння зі списком очікуваних інверторів. Це частина
задачі 12.
