# 09 — `discovery.js`

**Фаза:** 3 — Multi-inverter
**Залежності:** 04, 07
**Блокує:** 10

## Контекст

`db.js` створює таблицю `inverters` і експортує `upsertInverter()` (`db.js:47`), але **весь модуль не імпортований ніде** — `grep -rn "from './db.js'" --include='*.js'` дає нуль збігів. Локальна `data/bot.db` порожня: `inverters: 0`.

Без автовиявлення таблиця так і лишиться порожньою, а `/subscribe` не матиме до чого підписувати — валідація `getInverter(id)` завжди повертатиме «не знайдено».

Джерело істини — сам InfluxDB: колектор (задача 03) пише тег `inverter`, discovery його вичитує. Ручного реєстру інверторів не заводимо — інакше додавання нового об'єкта потребуватиме деплою.

## Кроки

1. Створити `discovery.js` з циклом раз на 5 хв.
2. Запит через існуючий `queryGrafana()` з `grafana.js`:
   ```flux
   import "influxdata/influxdb/schema"
   schema.tagValues(bucket: "<INFLUXDB_BUCKET>", tag: "inverter")
   ```
3. Для кожного значення — `upsertInverter()`. `dashboard_uid` за замовчуванням береться з `GRAFANA_DASHBOARD_UID`, `panel_id` — 6 (як у `db.js:17`).
4. Про **нові** (яких не було в БД) повідомити адміну через `ADMIN_CHAT_ID`. Про вже відомі — мовчати, інакше кожні 5 хв буде спам.
5. Зникнення тега з InfluxDB **не видаляє** інвертор з БД: retention бакета 30 днів, і мовчазне видалення знесло б підписки каскадом (`ON DELETE CASCADE` у схемі). Видалення — тільки вручну через адмінську `/remove_inverter`.
6. Помилка запиту не має валити цикл — залогувати й дочекатись наступної ітерації.
7. Виконати одну ітерацію одразу на старті, потім за інтервалом — інакше після деплою бот 5 хв не знає жодного інвертора.

## Критерії готовності

- [x] Після старту бота таблиця `inverters` містить рядок для реального інвертора
- [x] Повторні ітерації не плодять дублікатів і не шлють повторних повідомлень адміну
- [x] Поява нового значення тега → повідомлення адміну протягом 5 хв (код є; перевірити після заведення `ADMIN_CHAT_ID` у задачі 18)
- [x] Помилка Grafana в циклі discovery не зупиняє Telegram-полінг
- [ ] Перевірка:

  ```bash
    "node -e \"const db=require('better-sqlite3')('/app/data/bot.db'); console.log(db.prepare('select * from inverters').all())\""
  ```


## Результат (4 вер 2026)

```
discovery: новий інвертор 2512151417
discovery: новий інвертор test
```

У проді:
```json
[{"id":"2512151417","dashboard_uid":"0c5a65c2-…","panel_id":6},
 {"id":"test","dashboard_uid":"0c5a65c2-…","panel_id":6}]
user_version 1
```

6 тестів; розбір відповіді Grafana винесено в чисту `parseTagValues`.

### Наслідок, який варто знати

Фантомний тег `test` (від тестових записів задачі 01) потрапив у таблицю — і,
на відміну від самих точок, які retention зітре 3 жовтня, **рядок у БД
лишиться назавжди**. Правило «зникнення тега не видаляє інвертор» захищає
підписки від каскадного видалення, але так само зберігає й сміття.

Прибрати — командою `/remove_inverter` із задачі 11; це буде її жива перевірка.

### Зроблено понад задачу

Разом із цим у `index.js` з'явилось коректне завершення (SIGTERM/SIGINT →
`wal_checkpoint(TRUNCATE)` → `close()`) і обробники `unhandledRejection` /
`uncaughtException`. Формально це кроки 6-7 задачі 11, але вводити SQLite у
рантайм без них означало б свідомо лишити ризик, про який та задача попереджає.
