# 03 — Сервіс збору `collector/`

**Фаза:** 1 — Фундамент даних
**Залежності:** 01 (write-токен), 02 (формат API)
**Блокує:** 04

## Контекст

Це відсутня ланка всієї системи. Дашборд, алерти й бот читають з InfluxDB, куди зараз ніхто нічого не пише.

Колектор — **окремий процес**, не частина бота. Причина: у бота polling-цикл Telegram у тому ж event loop, а колектор має власний ритм, власні креденшели й власний профіль відмов. Падіння одного не має забирати інше.

Живе в цьому ж репо (`collector/`), деплоїться окремим Fly-застосунком у 04.

## Схема запису

Це контракт, від якого залежить решта системи — міняти його потім дорого:

```
measurement: battery
tags:
  inverter=<стабільний id пристрою>     # SN інвертора, див. .claude/deye.local.md
fields:
  soc         (float, %)      ← НЕ integer
  voltage     (float, V)
  current     (float, A, signed)
  power       (float, W, signed)   ← НЕ integer
  temperature (float, °C)
  state       (float, код)    ← НЕ string
timestamp: час виміру з Deye API (не час запиту)
```

Тег `inverter` — те, на чому тримається `schema.tagValues()` у discovery (задача 09), фільтр у панелях дашборда (08) і групування алерту (12). Значення має бути стабільним у часі: якщо взяти SN — воно таким і буде; якщо людську назву — вона може змінитись і породити дубль-серію.

### Типи не на наш вибір — вони вже задані (перевірено 2026-09-03)

Бакет `monitoring` порожній за даними, але **схема таблиці `battery` у ньому
збереглася** — InfluxDB 3 (IOx) тримає типи колонок незалежно від retention.
Спроба записати з «правильними» за первісною специфікацією типами дає HTTP 400:

```
table schema conflict - line has column 'soc' of type iox::column_type::field::integer
but table 'battery' has type iox::column_type::field::float
```

Перевірено записами по кожному полю:

| Спроба | Результат |
|---|---|
| `soc=42` (float) | 204 ✅ |
| `soc=42i` (integer) | 400 — конфлікт схеми |
| `power=57` (float) | 204 ✅ |
| `power=57i` (integer) | 400 |
| `state="charging"` (string) | 400 |
| `state=1i` (integer) | 400 |
| `state=1.0` (float) | 204 ✅ |
| усі 6 полів одним рядком (float) | 204 ✅ |

**Усі шість полів — float.** Змінити тип колонки в IOx неможливо; єдина
альтернатива — новий бакет (тягне новий read-токен і зміну datasource uid
у дашборді й алерт-правилі, тобто задачі 08 і 12). Не варте того.

Отже `state` пишемо **числовим кодом**, а не текстом:

| Код | Значення |
|---|---|
| `1` | заряджається (`power > 0`) |
| `0` | простій (`power == 0`) |
| `-1` | розряджається (`power < 0`) |

Це навіть краще за рядок: Grafana вміє порогувати числа й підставляти текст
через value mappings, а бот робить свій мапінг у текст сам. Знак `power` досі
не підтверджений емпірично — див. `docs/deye-cloud-api.md`.

### Успадкована колонка-тег `unit`

У схемі таблиці є зайвий тег `unit` від невідомого попереднього писача — саме
він давав дві окремі серії `soc` у легенді Grafana на скріншоті з 6 березня
(`soc {inverter="…", Unit="1"}` проти `soc {inverter="…"}`). Ми його **не
пишемо**; для наших точок він лишиться null і серії не розщепить.

### Видалити записане неможливо

`POST /api/v2/delete` на цьому бакеті віддає:

```
HTTP 405 {"code":"method not allowed",
          "message":"Deletes ranges are not supported for serverless v3 buckets"}
```

Тобто **будь-яке сміття, записане колектором, лежатиме всі 30 днів retention**,
і прибрати його не можна ніяк. Це піднімає вагу валідації діапазонів перед
записом з «бажано» до «обов'язково»: один баг з `NaN` чи SOC=6500 отруїть
дашборд і алерти на місяць.

Наразі в бакеті вже лежать тестові точки з тегом `inverter=test`
(3 вер 2026, ~17:17 UTC) — приберуться самі 3 жовтня. До того моменту
`schema.tagValues(tag: "inverter")` повертатиме зайве значення `test`,
що видно в discovery (задача 09) і у змінній дашборда (08).

## Кроки

1. `collector/index.js` — точка входу, цикл з інтервалом `COLLECT_INTERVAL`. Задача 02 виміряла реальний каданс хмари: **~10–15 хв** (зафіксовані інтервали 921 с і 614 с між `collectionTime`). Дефолт — **300 с**: удвічі частіше за оновлення, щоб не пропускати його більш ніж на один цикл, і без марних запитів. Частіше — безглуздо, хмара віддасть те саме закешоване значення.
2. `collector/deye.js` — клієнт Deye Cloud: отримання й кешування access token з проактивним refresh до закінчення TTL, список пристроїв, останні дані.
3. `collector/influx.js` — запис у InfluxDB через line protocol (`POST /api/v2/write?org=…&bucket=…&precision=s`), батчем по всіх пристроях за один запит.
4. `collector/config.js` — env-змінні (за зразком кореневого `config.js`).
5. Обов'язково:
   - `AbortController` з таймаутом на кожен fetch
   - ретраї з експоненційним backoff на 5xx і мережеві помилки
   - **timestamp виміру з API**, а не `Date.now()` — інакше при повторі запису з'являться дублікати замість перезапису точки
   - пропуск запису, якщо timestamp не змінився з минулої ітерації (хмара віддає ті самі дані між вивантаженнями логера)
   - логи без секретів: ніколи не логувати `appSecret`, токени й повний URL із токеном у query
   - валідація діапазонів перед записом (SOC 0..100 тощо) — сміття в бакеті потім не витравити

## Критерії готовності

- [x] `node collector/index.js` локально пише реальні дані в бакет
- [x] Дані видно — перевірено в Data Explorer консолі Influx:
  `battery,inverter=<INVERTER_SN> soc=98,voltage=54.86,current=1.08,power=60,temperature=27,state=1`
  за 2026-09-03T17:30:00Z
- [x] Тег `inverter` пишеться і читається (`SELECT DISTINCT inverter` → SN інвертора)
- [x] Повторний запуск не плодить дублікатів — другий цикл з тим самим
  `collectionTime` не робить запису взагалі
- [x] Симуляція недоступності Deye (`DEYE_BASE_URL` на неіснуючий хост) → ретраї,
  `Цикл впав: fetch failed` у лог, процес живий, health віддає 503
- [x] `grep` по `collector/*.js` не показує жодного логування секретів

## Що вийшло

`collector/` — 5 модулів + точка входу, **44 тести** на `node:test` (`npm test`),
без жодної тестової залежності.

| Файл | Відповідальність |
|---|---|
| `transform.js` | чисті функції: `dataList` → точка, валідація діапазонів, line protocol, дедуп |
| `deye.js` | клієнт Deye: кеш токена, проактивний і реактивний ре-логін, пагінація, таймаути, ретраї |
| `influx.js` | запис line protocol; ретраїть 5xx, не ретраїть 4xx |
| `retry.js` | експоненційний backoff з `shouldRetry` |
| `config.js` | env з валідацією; секрети неперелічувані, щоб не витекли в лог |
| `collector.js` | цикл: discovery → latest → валідація → дедуп → запис |
| `index.js` | точка входу, health-check, який **не бреше** |

Рішення, що варті згадки:

- **Помилка одного пристрою не валить цикл.** `toPoint` кидає, цикл ловить на
  кожен пристрій окремо і пише решту. Бита телеметрія одного об'єкта не
  позбавляє даних інші.
- **Health-check віддає 503**, якщо останній успішний цикл старший за
  `max(3 × інтервал, 5 хв)`. Це пряме виправлення того, через що бот пів року
  рапортував OK будучи мертвим.
- **Ретраїмо лише кинуті помилки** (мережа, таймаут). Ділові відмови Deye
  приходять тілом і від повторення валідними не стануть; 4xx від Influx — теж.

## Уточнення до `docs/deye-cloud-api.md`

Розвідка стверджувала, що **всі** відповіді Deye приходять з HTTP 200. Це не так:
помилки валідації параметрів віддаються з **400** і тілом `success:false`.
Спіймано на `size: 100` → `400 {"code":"2101006","msg":"size max 50"}`.
Тому клієнт парсить тіло незалежно від статусу, а статус згадує лише коли
тіла немає. Ліміт сторінки — 50, `listInverterSns()` пагінує за `stationTotal`.
