# 12 — Алерт по кожному інвертору окремо

**Фаза:** 3 — Multi-inverter
**Залежності:** 04, 08
**Блокує:** нічого

## Контекст

Прийнято рішення **лишити алертинг у Grafana**, а не переносити в бота (`alerts.js` з дизайн-доку не пишемо, таблицю `alert_state` прибрано в задачі 05).

Правило вже існує й налаштоване:
- uid `fff49r52vklc0d`, назва «🔋 Deye Battery SOC < 20%»
- папка `Deye Alerts` (`eff49ei1sgbuob`)
- datasource `aff44z3iv9fy8d`, `for: 1m`, `noDataState: NoData`
- contact point `Telegram Deye Battery` (`bff49136fkrnke`, тип telegram, з `bottoken` + `chatid`)
- поточний стан: **`nodata`** з 10 лип 2026 — вийде з нього автоматично після задачі 04

Проблема з кількома інверторами — у запиті:
```flux
from(bucket: "monitoring")
  |> range(start: -10m)
    |> filter(fn: (r) => r._measurement == "battery" and r._field == "soc")
      |> last()
        |> map(fn: (r) => ({r with _value: r._value}))
```
Джерело не розрізняється. Далі йде reducer `last` і поріг `< 20`. З двома інверторами:
- Grafana отримає кілька серій там, де очікує одну → або помилка «input data must be a wide series», або схлопування в одне значення
- навіть якщо спрацює, повідомлення «SOC < 20%» **не скаже, у кого саме сів акумулятор** — для волонтерського проєкту з кількома об'єктами це робить алерт майже марним

## Кроки

1. Переробити запит A на multi-dimensional — щоб кожен інвертор давав власний alert instance:
   ```flux
   from(bucket: "monitoring")
     |> range(start: -10m)
     |> filter(fn: (r) => r._measurement == "battery" and r._field == "soc")
     |> group(columns: ["inverter"])
     |> last()
   ```
2. Переконатись, що `inverter` доїжджає як label інстансу (у Grafana теги InfluxDB стають labels). За потреби додати `keep(columns: ["_time","_value","inverter"])`.
3. Додати `{{ $labels.inverter }}` в анотації summary/description і в шаблон повідомлення contact point.
4. Перевірити `noDataState`. Зараз `NoData` — якщо колектор для одного з інверторів замовкне, прийде окремий NoData-алерт. Це радше корисно (мовчазний інвертор — теж інцидент), але треба свідомо підтвердити, а не лишити випадково.
5. Розглянути другий поріг (наприклад, SOC < 10% як critical) — окремим правилом, не перевантажуючи це.

Зручно робити через provisioning API:
```
GET /api/v1/provisioning/alert-rules/fff49r52vklc0d
PUT /api/v1/provisioning/alert-rules/fff49r52vklc0d
```

## Критерії готовності

- [ ] Правило у стані `Normal` (не `nodata`, не `error`) після появи даних
- [ ] З двома інверторами в бакеті — **два окремі alert instances** з різними labels
- [ ] Попереднє обчислення в редакторі правила не дає «input data must be a wide series»
- [ ] Тестове повідомлення в Telegram містить назву конкретного інвертора
- [ ] Штучне падіння SOC нижче порогу (тимчасово підняти поріг до 99) дає алерт саме по потрібному інвертору

## Нотатка

Алерти йдуть в один захардкоджений чат із contact point, а не підписникам конкретного інвертора — це усвідомлений компроміс обраного рішення. Якщо згодом знадобиться персональна розсилка по підписках, доведеться повертатись до `alerts.js` у боті; тоді доцільно лишити правило в Grafana лише як страховку для адміна, щоб не дублювати повідомлення користувачам.
