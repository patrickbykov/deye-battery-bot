# 21 — Перевести Grafana на вебхук

**Фаза:** 5 — Користувачі та персональні алерти
**Залежності:** 20
**Блокує:** 24

## Контекст

Код готовий — лишається під'єднати Grafana. Робиться в UI/через provisioning
API, коду не змінює.

**Наявний telegram-contact point лишається** — рішення власника. Якщо бот
лежить або вебхук зламався, адмін усе одно дізнається про проблему напряму
від Grafana. Ціна — адмін отримає два повідомлення, якщо він ще й підписник.
Нотатка в задачі 12 радила саме це.

## Кроки

1. Створити contact point типу `webhook`:
   - URL `https://deye-battery-bot.fly.dev/hooks/grafana`
   - `httpMethod: POST`
   - `authorization_scheme: Bearer`, `authorization_credentials: <токен>`
   - `max_alerts: 20` — щоб верхня межа розміру payload була керована з обох
     боків (ліміт тіла 256 KB виставлений у задачі 16)
2. У notification policy лишити **обидва** receiver'и: telegram для адміна,
   webhook для користувачів.
3. Перевірити кнопкою Test у contact point — і **подивитись реальну структуру
   payload**, вона може відрізнятись від задокументованої версією Grafana.
4. Живий тест, тим самим способом, що застосовувався 3 вер 2026:
   - тимчасово підняти поріг SOC до 99 → повідомлення має прийти адміну **і**
     схваленому підписнику, і **не** прийти `pending`. Повернути 20.
   - тимчасово звузити вікно правила простою до `-1m` → лише адмін.
     Повернути `-45m`.
5. Після переходу перевірити `lastNotifyAttemptError` обох contact point'ів:
   ```
   GET /api/alertmanager/grafana/config/api/v1/receivers
   ```
   Порожньо = доставка йде. Це єдине місце, де видно провал доставки: в UI
   правило показує здоровий `firing`, ніби все спрацювало.

## Критерії готовності

- [x] Тестове сповіщення з UI Grafana доходить у бота (видно в `fly logs`)
- [x] Живий алерт SOC доходить адміну **і** схваленому підписнику
- [x] Той самий алерт **не** доходить `pending` користувачу
- [x] Алерт застою доходить лише адміну
- [x] `lastNotifyAttemptError` порожній в обох contact point'ів
- [x] Пороги й вікна повернуті на робочі (20% і 45 хв)


## Результат (4 вер 2026)

Webhook-інтеграцію додано **під тією самою назвою**, що й telegram:
у Grafana contact point — це група інтеграцій зі спільним ім'ям, тож
`bottoken` чіпати не довелось (а він віддається як `[REDACTED]`, і PUT
на contact point ризикував би його затерти).

Правила використовують спрощений роутинг (`notification_settings`), який
обходить дерево політик, — тому окремий contact point вони б не побачили.

Живий тест: поріг тимчасово 99 при SOC 98.
```
06:10:55  Вебхук: 1 алерт(ів) [firing inverter=2512151417]
06:10:55  Алерт «🔋 Заряд батареї нижче 20%» → 1 адресат(ів)
```
У Telegram прийшло **два** повідомлення: від telegram-каналу адміна і від
бота як підписнику. Це очікувана ціна страхувки для адміна, який ще й
підписник. Пороги повернуто: 20%, `for: 1m`, вікно 45 хв, `noDataState: OK`.

## Перегляд рішення (14 вер 2026)

Дубль виявився не рідкісною ціною, а нормою: адмін отримує **кожен** алерт
двічі — з назвою обʼєкта від бота і з голим серійником від Grafana. Бот
додає адміна до кожного адресного алерту, тож умова «якщо він ще й підписник»
виконується завжди.

Telegram-інтеграцію прибрано з `Telegram Deye Battery`. Страхувку «бот
лежить» тепер тримає перевірка Synthetics на `GET /` з окремим contact point.
Подробиці — `docs/grafana-alerting.md`, розділ «Страхувка без дубля».
