# 02 — Розвідка Deye Cloud OpenAPI

**Фаза:** 1 — Фундамент даних
**Залежності:** немає
**Блокує:** 03

## Контекст

Інвертор Deye SUN-15K-SG05LP3-EU-SM2 сам нікуди нічого не пише. WiFi-логер SM2 вивантажує телеметрію в хмару Deye, і саме звідти колектор має її забирати.

Обрано хмарний API, а не локальний Solarman V5, бо далі планується підключати чужі об'єкти, до LAN яких доступу не буде (детальне обґрунтування — у плані).

Це **задача-дослідження**: без реального формату відповіді писати 03 — це писати наосліп. Публічна документація по ендпойнтах і лімітах фрагментарна, тому все треба зафіксувати з живих запитів.

## Кроки

1. Зареєструвати застосунок на https://developer.deyecloud.com/ (вхід тими ж креденшелами, що й Deye Cloud). Отримати `appId` + `appSecret`.
2. Пройти flow отримання access token. Зафіксувати: URL, тіло запиту, TTL токена, чи є refresh.
3. Знайти й перевірити ендпойнти:
   - список станцій (`station/list` або аналог)
   - список пристроїв станції
   - **останні дані пристрою** — головний ендпойнт для колектора
4. Зафіксувати серійний номер свого інвертора/логера.
5. З'ясувати емпірично:
   - як реально називаються поля батареї (SOC, напруга, струм, потужність, температура, стан)
   - фактична частота оновлення даних у хмарі (запитати той самий пристрій кілька разів з інтервалом і порівняти timestamp)
   - чи є timestamp виміру у відповіді, чи тільки час запиту — від цього залежить ідемпотентність запису в 03
   - поведінка при протуханні токена й при перевищенні лімітів
6. Записати все в `docs/deye-cloud-api.md`: живі curl-приклади, приклад відповіді (з відредагованим SN), таблиця відповідності полів схемі InfluxDB.

## Критерії готовності

- [ ] `appId`/`appSecret` отримано, зберігаються поза репо
- [ ] Access token видається робочим curl-запитом
- [ ] Отримано реальну відповідь з даними батареї свого інвертора
- [ ] `docs/deye-cloud-api.md` створено й містить: auth flow, ендпойнти, приклад відповіді, мапінг полів, TTL токена, виміряну частоту оновлення
- [ ] Зафіксовано серійник пристрою

## Мапінг, який треба підтвердити

Колектор у 03 має писати саме таку схему — вона задає весь multi-inverter дизайн:

| Поле InfluxDB | Поле Deye API | Одиниці |
|---|---|---|
| `soc` | ? | % |
| `voltage` | ? | V |
| `current` | ? | A (signed) |
| `power` | ? | W (signed) |
| `temperature` | ? | °C |
| `state` | ? | текст/enum |
| тег `inverter` | SN пристрою або людський id | — |

## Довідка: локальний варіант (не реалізуємо зараз)

Якщо колись знадобиться читати інвертор напряму в LAN — TCP:8899, Modbus RTU у протоколі Solarman V5, потрібні IP логера + серійник, бібліотека `pysolarmanv5`. Регістри 3-фазних гібридів Deye, FC `0x03`:

| Метрика | Регістр | Перетворення |
|---|---|---|
| Температура | `0x024A` (586) | ×0.1, offset 1000 |
| Напруга | `0x024B` (587) | ×0.01 V |
| SOC | `0x024C` (588) | % |
| Потужність | `0x024E` (590) | W, signed |
| Струм | `0x024F` (591) | ×0.01 A, signed |
